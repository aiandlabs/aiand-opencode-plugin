# Aiand PDF Chunking Final Fix Report

**Date:** 2026-08-15
**Branch:** `feat/pdf-support`
**Reviewed head:** `1ec53919c04b115e004231616d209b149e845a6a`
**Scope:** Single final-review fix wave; no push and no pull request.

## Outcome

All five Important findings and both Minor findings were reproduced with discriminating tests and fixed. The production bridge now consumes a visitor-based PDF preparation primitive that loads one source document per pass and awaits the consumer for each chunk before serializing the next. The compatibility `preparePdfChunks()` API remains array-returning for existing callers and component tests, but production does not call it.

During GREEN verification, stricter freshness publication exposed an additional loop hazard when an upload response supplied a numerically valid lease that was already unsafe. A dedicated RED test was added; the bridge now rejects that response once with the fixed content-safe error `[aiand] PDF upload response failed: unusable file expiry` and does not cache, retry, or dispatch chat with the ID.

## Finding-by-finding changes and evidence

### Important 1 — PDF pre-detection shape and media-type boundary

- Added unsupported-catalog passthrough cases for a non-file part carrying PDF data and a file part declaring `application/pdfx`.
- RED: both cases threw the unsupported capability error instead of reaching the unchanged chat passthrough.
- GREEN: one shared `inlinePdfCandidate()` structural predicate now requires `type === "file"`, an object `file`, a string `file_data`, and a real `application/pdf` data-URL boundary (`;` or `,`). `inlinePdfPart()` applies exact canonical `data:application/pdf;base64,...` validation only after that predicate.
- Existing canonical validation ordering and malformed-PDF fixed errors remain unchanged.

### Important 2 — sequential uploads across distinct attachments

- Added a two-message/two-distinct-PDF transport test with an active-upload counter.
- RED: maximum concurrent uploads was `2`.
- GREEN: message and content traversal use sequential `for...of` loops; maximum active upload count is `1`, transformed output order remains `file-1`, `file-2`, and surrounding request structure is preserved.

### Important 3 — hard source-byte ceiling

- Added creation-time invalid-option cases for `NaN`, `Infinity`, zero, negative, and fractional values.
- RED: the bridge accepted the invalid values.
- Added a direct normalization boundary test for a valid override above 100 MiB.
- RED: the production normalization export was absent.
- GREEN: `normalizeMaxPdfBytes()` rejects non-positive/non-safe-integer values and clamps valid values to `100 * 1024 * 1024`; smaller test limits remain supported. `createPdfUploadFetch()` uses the normalized value before decoding.

### Important 4 — page-count parser error redaction

- Added a hand-built, loadable PDF fixture whose page tree has a numeric `/Kids` value.
- The fixture proves `PDFDocument.load()` succeeds and `getPageCount()` throws.
- RED: the raw `pdf-lib` message `Expected instance of PDFArray, but got instance of PDFNumber` escaped.
- GREEN: loading and page counting are in the same parser guard and return only `[aiand] PDF split failed: document could not be processed`.

### Important 5 — aggregate emitted-chunk retention

- Added `visitPdfChunks(bytes, visitor, options)` and retained `preparePdfChunks()` as a compatibility wrapper implemented by collecting visitor results.
- Component RED: importing `visitPdfChunks` failed because the export did not exist.
- Component GREEN: a 201-page backpressure test monkey-patches `PDFDocument.create` and proves only one chunk document has been created while the first visitor is blocked; all three are created only as each visitor completes.
- Transport RED: a dependency seam that makes array preparation fail produced `array preparation must not be used` before upload.
- Transport GREEN: production calls the visitor seam, hashes and resolves/uploads the current generated bytes inside the visitor, retains only `{ digest, lease }` while preparing, and generates the next chunk only after the visitor returns.
- Settled manifests remain `FileLease[]` only. No chunk bytes, parser objects, filenames, multipart bodies, credentials, or response content enter settled manifest values.
- Publication uses a synchronous current-identity-and-freshness check. If any chosen leaf was replaced or became unsafe, the source is deterministically re-streamed. Current leaves are reused by digest; only mismatched/unsafe leaves upload again.
- A real-pdf shared-prefix race replaces the earlier fabricated chunk dependency. It proves two different 101-page PDFs share a deterministic first leaf, a stale response replaces that leaf during the other source's later upload, source A is re-streamed, the current shared leaf is reused, and the settled source-A manifest contains the new shared ID plus its original unique ID.
- The existing preparation seam now counts calls while delegating to the real visitor. Concurrent identical sources still show exactly one source preparation and one leaf upload set.

### Minor 1 — freshness at manifest publication

- Added a fake-clock test where chunk 1 is fresh when uploaded, then expires while chunk 2 uploads.
- RED: only two uploads occurred and the manifest published the stale first ID.
- GREEN: publication requires both `leases.get(digest) === lease` and `now() < expiresAtMs - expirySafetyMs` without an intervening await. The source is re-streamed, chunk 2 is reused, chunk 1 is refreshed, and chat receives only fresh IDs.
- Updated the settled mixed-expiry fixture so both leases are initially publishable and one later enters the safety window, preserving the original partial-reuse behavior without publishing an initially unsafe lease.

### Minor 2 — catalog logging redaction

- Added exact `console.error` capture tests for HTTP and thrown transport failures.
- RED: HTTP logging included `statusText`; thrown failures logged the complete exception and its private transport detail.
- GREEN: HTTP failures log exactly `[aiand] model catalog fetch failed: HTTP <numeric status>`; caught failures log exactly `[aiand] model catalog fetch failed` with no second argument.

## Self-review

- **Request/body/header semantics:** sequential traversal preserves message/content order and unrelated values. Upload requests retain safe headers, remove inherited multipart `content-type` and stale `content-length`, use `purpose=document`, and keep `redirect=error`. Chat dispatch removes stale `content-length` and contains no inline PDF data.
- **Cache races:** source and leaf singleflight remain independent; incomplete manifests are never published; successful partial leaves remain reusable; stale compare-and-delete invalidation is unchanged; publication has no await between leaf identity/freshness checks and `manifests.set`.
- **Memory retention:** production never invokes the array wrapper. Each generated chunk is hashed and awaited through lease resolution before the visitor returns. Preparation retains only source bytes plus per-leaf digest/lease metadata; settled manifests contain only file IDs and expiry timestamps.
- **Sequencing:** one request prepares/uploads distinct attachments serially and each source emits/uploads chunks serially. Concurrent requests can still share source/leaf in-flight promises as required.
- **Error and log redaction:** parser detail, provider messages outside the existing strict allowlist, catalog status text, thrown catalog errors, PDF data, filenames, full digests, credentials, and arbitrary transport detail are not exposed.
